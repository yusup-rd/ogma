# Ogma architecture

## Application boundaries

- Use a Yarn workspaces monorepo with `apps/web` for Next.js App Router, `apps/api` for NestJS, `packages/contracts` for shared validation and types, and `packages/resume-renderer` for document rendering. Use strict TypeScript throughout.
- Next.js serves the dashboard and editor. NestJS owns data access, revisions, imports, exports, analysis, and integrations. Route browser `/api` traffic to NestJS on the same origin. Keep PostgreSQL accessible from the backend only.
- Use Prisma migrations for relational data and PostgreSQL JSONB for validated, versioned document payloads. Share payload validation with Zod where the editor and API both use the same shape. Use React Hook Form for structured fields. Add dnd-kit only if it meets the editor’s pointer and keyboard reorder needs.

## Data and editing

- `Owner` stores the configured identity. `LibraryEntry` stores a typed entry with a stable ID, current revision, and archive state. `LibraryEntryRevision` keeps immutable validated content, with stable IDs for nested bullets and skills so selections survive a sync. Use archival to keep previous selections resolvable.
- `Resume` stores the owner, title, draft revision counter, and current document payload. The payload contains section definitions and labels, order, entry and bullet selections, pinned source revisions, CV-specific overrides, template versions and per-template styles, and asset references. A presence check distinguishes an explicit blank override from inheriting a source field. Use `schemaVersion` and migrate old payloads on read before the next write.
- Resolve a CV by combining its pinned content, selections, overrides, and template defaults into one ordered document model. Hidden content stays available to the editor and is excluded from the rendered model. A library update leaves existing CVs stable until sync. Preview changed fields, preserve local edits, and ask how to resolve overlapping edits or selected bullets removed in the library update. New bullets on existing entries start unchecked on sync. Allow users to copy tailored text back into the library explicitly.
- `ResumeCheckpoint` stores an immutable payload, resolved content, template version, and asset references. Restoring creates a fresh draft revision and preserves the checkpoint. Duplication creates a new CV with copied draft settings and identical pinned sources. Retain versioned fonts, templates, and assets referenced by saved checkpoints. When a CV is marked sent, save the actual exported file if available for an exact historical record.
- `Asset` stores ownership, media type, size, and a private storage key. Store uploaded photos in private object storage. Keep references to photos used by drafts or checkpoints when cleaning up unattached assets.
- `AnalysisRun` records the draft revision, resolved document fingerprint, target export format, rubric version, category breakdown, and diagnostics. Later, `Job` stores the manually entered posting and status, `JobMatchRun` records the CV and job input fingerprints, `CoverLetterDraft` stores editable text linked to a job, the source CV revision or checkpoint, and the job description fingerprint, and `JobSubmission` links to the exact checkpoint sent. Retain sent records when a draft is archived.

## API and consistency

- Store renamed section titles at CV level in `sectionTitles`, and merge them into the resolved style for preview and exports. Preserve older per-template titles as a fallback until a user renames that section. Keep unsaved Content drafts in a separate preview layer; only Save updates persisted content. Cancel removes that section’s preview draft without affecting other edited sections. Require saved sections before exports and checkpoint actions.

- Provide REST resources under `/api` for the library, CVs, checkpoints, assets, imports, exports, and analysis. Add explicit actions for duplicate, restore, and sync so each action checks authorization and runs atomically. Model links between related records with foreign keys and enforce ownership at the API boundary.
- Apply edits locally as the user types. Debounce persistence, serialize saves, and send the expected draft revision with each write. Reject stale writes with a conflict response and offer to reload the current copy or preserve the local draft as a separate CV. Keep unsaved fields recoverable in memory on transient failures and expose retry. Confirm the draft revision before starting an export or analysis.
- Use idempotency keys on retryable create, duplicate, restore, and import-commit actions. Commit multi-record changes in transactions. Render jobs take immutable input snapshots and report the analyzed/exported revision even if another device edits the CV while the work runs.

## Pagination and formats

- Use a portable resolved model for preview, PDF, DOCX, and analysis. Define typed template metadata, supported controls, and bounds for design values. Store document measurements in millimeters and points, with unitless line height. Use validated, scoped CSS custom properties for runtime styling.
- Prototype a shared React document renderer and pagination routine for HTML preview and Playwright Chromium PDF. Measure at actual A4 dimensions after fonts and images are ready. Scale only the preview viewport. Keep headings with their first item and prefer breaking between entries or bullets. Split oversized text at measured line boundaries and surface an actionable warning if layout constraints cannot be met. Respect manual section breaks without creating extra blank pages.
- Print the paginated A4 markup with explicit print CSS and pinned Chromium, using PDF page dimensions from CSS. Package matching licensed font files with Cyrillic coverage in both preview and render runtime. Validate page count, line wraps, link behavior, selectable text, and reading order with English and Cyrillic fixtures. Use PDFs produced by the server as the reference for pagination when browser font metrics vary. [Playwright PDF API](https://playwright.dev/docs/api/class-page#page-pdf)
- Generate editable DOCX with `docx`, using A4 section properties, real Word headings, lists, paragraphs, links, inline photos, and supported spacing and page breaks. For multi-column templates, use a clearly labeled single-column Word export initially. Use widely available Cyrillic-capable font fallbacks and explain that Word pagination can vary with installed fonts and the editor. Check the result in Word or LibreOffice. [docx API](https://docx.js.org/api/)
- Use PDF.js for PDF text extraction. Evaluate Mammoth raw-text extraction for DOCX, adding structured paragraph or list extraction only where needed for useful field mapping. Detect image-only PDFs and provide a manual entry path. Present the extracted sections, ambiguous fields, and unmapped text for review. Keep the draft pending until the user commits. Validate file type and limits, bound parser time and decompressed size, and expire staged uploads. Treat extracted text as plain text. [PDF.js](https://github.com/mozilla/pdf.js) · [Mammoth](https://github.com/mwilliamson/mammoth.js#readme)

## Resume scoring and suggestions

- Start with a versioned 100-point rubric: 40 points for extractable text and reading order, 25 for clear structure and relevant core fields, 20 for layout legibility, and 15 for formatting consistency. Calibrate on fixtures before finalizing weights. Keep general editorial advice, such as suggestions to quantify impact, separate from parser findings. Condition field checks on what is relevant to the CV and handle custom titles using section types and heading structure.
- Analyze the selected CV using its resolved content and the actual selected export artifact. Extract text and compare normalized text, expected section order, representative field presence, and link labels. Flag missing or garbled text, clipping and overflow, columns with shuffled reading order, headings detached from content, and critical data embedded only in images. Flag potential issues with photos or columns proportionately, using extraction to distinguish advisories from observed failures. If extraction fails, report an incomplete run instead of awarding unverified points.
- Save stable rule IDs and findings with a severity, score impact, field or page reference, and fix. English heuristics run only where applicable. Normalize results over applicable checks and expose skipped checks. A score of 90+ means the document passed most of Ogma’s checks. [Greenhouse resume parsing guidance](https://support.greenhouse.io/hc/en-us/articles/200989175-Unsuccessful-resume-parse)
- Keep AI behind a server-side, opt-in rewrite action. Configure the provider endpoint, model, and credentials through `AI_BASE_URL`, `AI_MODEL`, and `AI_API_KEY`. Start with an OpenAI-compatible endpoint behind a provider interface. Add adapters for other protocols as needed. Show the selected text before sending and exclude contact fields and photos. Validate structured responses, display a before/after preview, and apply the edit only after approval and a fresh revision check. Keep the scoring rubric independent of inference. Handle timeout, rate limits, and invalid output without changing the CV. Before enabling the integration, verify model availability, account limits, and retention settings.
- For Job Match, start with weighted phrases and skill aliases in the pasted description, deduplicated with Unicode-aware matching. Show the evidence behind matches and distinguish included CV content, available library content, and missing evidence. Report insufficient information when the posting has no usable requirements. Keep this score independent of the structure score.

- Cover letter drafting uses the same server-side provider and consent flow as CV rewrites. Send only the selected CV evidence and relevant job description text after approval. Keep suggestions grounded in the selected experience. Validate the response, present the draft for review, and save user edits explicitly. Keep the saved letter available if its source changes and show when the draft was based on an earlier CV or job description. Support manual drafting when the provider is unavailable.

## Hosting and verification

- Deploy privately behind HTTPS on the proposed subdomain. Start with a single allowlisted owner using an OIDC provider, disabled public signup, secure same-origin session cookies, CSRF protection for mutations, and server-side checks on downloads. Select the hosting and identity providers during foundation based on Chromium support, backups, and cost.
- Use a container-capable NestJS runtime for Chromium and parsers, a private PostgreSQL instance, and private object storage. Generate documents with bounded concurrency and timeouts, isolated browser contexts, and bundled assets. Use short-lived private download URLs or streams. Log timings and errors with request IDs and omit CV text, job descriptions, and provider payloads. Keep secrets in runtime configuration. Back up the database and assets together and rehearse restoration.
- Cover conflicts, duplication, checkbox and sync behavior, checkpoint restore, parser edge cases, scoring, and export reading order with focused tests. Run one end-to-end flow from import through export and verify the private flow on desktop, mobile Safari, and a second signed-in device. Use representative one-page, multi-page, photo, no-photo, and Cyrillic fixtures. Check keyboard order, focus management, reduced motion, and preview overflow before the core release.
